VegVault Changelog

This page lists every version of VegVault and gives each release its own section, newest first. Each section says what changed against the release before it and what that means for code written for the earlier release. Every database file records its version in its version_control table, and the R package {vaultkeepr}, from its version 0.2.0, reads it when it opens the file.

VegVault 2.0.0

VegVault 2.0.0 is the second release. It is rebuilt from tagged, checksum-verified releases of the vegetation, fossil pollen, trait and abiotic data, with audited trait units and a corrected linkage of gridpoints to samples. It is also about 17 times smaller than 1.0.0 (6.5 GB instead of 110 GB) and, read with {vaultkeepr} 0.2.0, about 48 times faster to query than 1.0.0 was with {vaultkeepr} 0.1.0. Its SQLite database (10.48700/y3p8y-g8106) and its flat files (10.48700/gpf0m-ptq85) are deposited in the EOSC CZ data repository as new versions of the 1.0.0 records.

TipMoving from 1.0.0 to 2.0.0

Running the same code with VegVault 2.0.0 and {vaultkeepr} 0.2.0 may return different data than with VegVault 1.0.0 and {vaultkeepr} 0.1.0. The sections below describe what changed.

Smaller and faster

The database file is 6.5 GB (6,509,383,680 bytes) against 110 GB for 1.0.0, mostly because the links between samples and gridpoints are stored once per position (see The schema).

The nine example workflows of the {vaultkeepr} articles were timed from opening the database to the extracted table, each five times, taking turns with the others, on one computer (24 cores, 64 GB RAM) on 2026-11-26 (benchmark on VegVault issue 84). The table gives the median time in seconds. {vaultkeepr} 0.1.0 did not run the workflows marked “not run”: its geographic window does not apply to trait datasets, which these workflows would then include from the whole world, so their results cannot be compared (see Which {vaultkeepr} reads which version).

The workflows that both versions of {vaultkeepr} ran took 126.11 s together with {vaultkeepr} 0.1.0 on 1.0.0 and 2.65 s with {vaultkeepr} 0.2.0 on 2.0.0, about 48 times faster; single workflows ran between 7 and 314 times faster. Most of the gain comes from {vaultkeepr} 0.2.0, which narrows a query to the selected samples before it classifies taxa or reads references and age uncertainty: with the same {vaultkeepr} 0.2.0, most workflows take about as long on 2.0.0 as on 1.0.0. One query is slower on 2.0.0: get_traits() with its default, the original taxon names, took 79.39 s against 0.28 s on 1.0.0, because {vaultkeepr} 0.2.0 joins all trait values with the new unit tables before it narrows them to the selection (vaultkeepr issue 77).

Which {vaultkeepr} reads which version

{vaultkeepr} 0.2.0 reads both VegVault 1.0.0 and 2.0.0. It opens the database read-only and reads its version when it opens it. With 2.0.0, get_traits() also returns the unit of each trait value and the keys of the rules that converted or derived it (trait_unit, conversion_rule_key and derivation_rule_key).

{vaultkeepr} 0.1.0 also opens a 2.0.0 database, runs without error and returns the same values for the same selection. But its geographic window does not apply to trait datasets: a trait workflow returns all 222,455 trait datasets of the database, wherever they lie, and it is up to about 180 times slower than {vaultkeepr} 0.2.0 (check on VegVault issue 84). Use {vaultkeepr} 0.2.0 with VegVault 2.0.0.

Identifiers and names

  • Database ids are numbered anew in every build, the trait domains included. Ids saved from 1.0.0 cannot be joined to 2.0.0.
  • Some names changed: BIEN plot datasets are named by their BIEN plot identifier (such as bien_CTFS__P01) instead of a row number (such as bien_1), fossil pollen samples by the Neotoma dataset id instead of the 1.0.0 database id (fossilpol_91256_21011 became fossilpol_1001_21011), and trait samples by the observation id of their source.
  • Unchanged: the names of the gridpoints (geo_<long>_<lat> and geo_<long>_<lat>_<age>), the names of the trait domains (including “Plant heigh”) and the names of the abiotic variables.

Select your data again by place, age, dataset type or taxon rather than by saved ids or names.

The schema

The database has 34 tables, 1 view and 123 columns. The Database Structure page describes each table.

  • Links are stored once per position. A position is a place and age shared by samples. The new tables Positions, SamplePosition and PositionLink hold the links between positions and gridpoints, and AbioticDataReference, a table in 1.0.0, is now a view with the same columns (sample_id, sample_ref_id, distance_in_km and distance_in_years), one row per sample and gridpoint. Code that reads AbioticDataReference works as before.
  • The flat files have no file of AbioticDataReference, because the view returns 2,007,681,491 rows. Join SamplePosition and PositionLink by position_id instead: the result has the columns of the view.
  • New tables and columns for trait units: TraitsDomain has a trait_unit, and TraitsValue has trait_unit_conversion_id and trait_derivation_id, which point to the new tables TraitUnitConversion and TraitDerivation (see Plant traits).
  • The build is recorded in the database: version_control has the new columns build_profile, git_commit and manifest_sha256 (the SHA-256 of the list of input files), and the new table BuildProducers lists every input of the build with its release tag.
  • Keys and checks: dataset and sample names are unique and never empty, the link and reference tables have composite primary keys, trait values are keyed on dataset, sample, trait and taxon, and coordinates must lie on the globe. Of the 59 secondary indexes of 1.0.0, the 29 that repeat another index or key are dropped (database design, decision 3).
  • Unchanged on purpose: the misspelt column trait_domanin_description of TraitsDomain, and the storage of gridpoints as datasets and samples.

Links between samples and gridpoints

A sample is linked to a gridpoint when the two are at most 50 km and at most 5,000 years apart. 1.0.0 used the same rule, but searched only within one degree of longitude and did not wrap at the dateline, so it missed some links. 2.0.0 applies the rule exactly. Run on the 1.0.0 inputs, it keeps every link of 1.0.0, with the same distances, and adds 427,097 links (0.45%) at 6,572 positions: 420,983 at high latitudes, where 50 km is more than one degree of longitude, and 6,114 across the dateline (comparison on VegVault issue 84).

The view AbioticDataReference returns 2,007,681,491 links in 2.0.0, against 2,067,445,952 rows of the table in 1.0.0. Because the rule of 2.0.0 keeps every link of 1.0.0 on the same inputs, the lower total comes from the samples of 2.0.0, which differ from those of 1.0.0 (see the sections below).

Climate and soil

  • bio4 (temperature seasonality) is corrected. In 1.0.0 it was 0 at age 0 at every gridpoint south of about 65.7° N, because of a truncated download (VegVault issue 78). This affects every vegetation plot and every fossil pollen sample that takes its climate from age 0.
  • The unit label of bio4 is now “C/100 (hundredths of a degree Celsius)”, which matches its values; in 1.0.0 it read “C (degree Celsius)”. The values themselves were already in hundredths of a degree.
  • Present-day annual precipitation (bio12) of 6,553.5 kg m⁻² is a lower bound. CHELSA V2.1 stores it as whole numbers of 0.1 kg m⁻² of at most 65,535, so wetter places are stored as 6,553.5 kg m⁻² (note on VegVault issue 84). This is unchanged from 1.0.0, and now documented.
  • A precipitation artefact of CHELSA-TraCE21k is masked: bio12, bio15, bio18 and bio19 have no value in a block of South America (25° S to 5° N, 80° W to 35° W) at 12,000, 12,500 and 15,000 to 18,000 years before present, where the source shows inflated precipitation (note on VegVault issue 84).
  • Zero precipitation in dry seasons: CHELSA-TraCE21k stores precipitation in whole kg m⁻², so a quarter with less than 0.5 kg m⁻² is 0 in the past, while the present-day values come in steps of 0.1 kg m⁻² (check on VegVault issue 96). In the Sahel and the Sudanian belt, the coldest quarter of bio19 can be the dry winter in one product and the rainy season in the other.
  • Soil groups are rebuilt from HWSD v2.2; 1.0.0 labelled them WoSIS and SoilGrids. The codes 1 to 32 of HWSD2 are the WRB 2022 Reference Soil Groups in alphabetical order, and they cannot be compared with the codes of 1.0.0, which came from a wrong lookup (note on VegVault issue 84). The legend is Outputs/Tables/hwsd_soil_group_legend.csv in the abiotic data repository. A gridpoint whose dominant class is not a soil (glaciers, open water) has no soil value. 2.0.0 has 83,925 soil values at gridpoints, against 73,808 in 1.0.0.

Plant traits

  • Every trait value is in one unit per trait domain, converted from the unit of its source by a recorded rule. TraitUnitConversion holds 65 conversion rules and TraitDerivation 1 derivation rule (leaf mass per area from specific leaf area). Some values differ from 1.0.0 by a unit factor; for example, leaf area is now in mm² instead of cm².
  • The audit of the units is attached to the trait data release: a summary and a reconciliation of the units of each source (trait_unit_audit_summary_*.csv and trait_unit_reconciliation_*.csv), with the tables of the other checks of the trait data (VegVault issue 76).
  • TRY is kept, with TRY’s standardised values. In 1.0.0, 45.6% of the TRY values did not match the standardised value of their record. Repeated measurements are removed, including BIEN records that copy TRY (trait data release notes). The TRY reference of each record is stored as a sample reference.
  • Counts: 897,183 TRY values in 28,272 datasets (1.0.0: 1,205,168 in 32,342), and 10,023,769 BIEN values in 194,183 datasets (1.0.0: 10,161,055 in 194,788). BIEN trait samples without a value are dropped (database design, decision 4).
  • BIEN trait records that name no provider have no data source. The data source of a BIEN trait record is the principal investigator of its BIEN project, and 7,869 BIEN plant-height values in 3,609 datasets name none. In 2.0.0 their data_source_id is empty; in 1.0.0 they pointed to a data source without a description, so neither version names their provider (check on VegVault issue 167). {vaultkeepr} returns NA as their data_source_desc in both versions, but code that joins every dataset to a data source drops these records in 2.0.0.

Vegetation, fossil pollen and taxa

  • Fossil pollen: a fresh download of the Neotoma Paleoecology Database and a full rerun of the FOSSILPOL workflow give 1,551 datasets with 100,341 samples, against 1,393 and 88,423 in 1.0.0 (FOSSILPOL release notes).
  • Vegetation plots: every plot has at most one record per taxon, and re-surveyed BIEN plots keep only their latest survey: 24,161 BIEN plots with 524,439 taxon records, against 24,233 and 972,791 in 1.0.0, and the same 67,022 sPlotOpen plots in both versions (vegetation data release notes).
  • Taxon names are classified again. Two kinds of names are corrected by hand: the 116 fossil pollen types that combine two or more taxa (such as “Betula/Carpinus”) keep only what their parts share, the family when all parts belong to one family (80 types) and no classification otherwise (36 types), and “Pinus Picea” is classified as Pinaceae instead of Abies alba (decision record on VegVault issue 86). Some errors of 1.0.0 are gone: for example, 1.0.0 classified the pollen type Alnus viridis as the genus Atanus, a leafhopper (comparison on vaultkeepr issue 51).
  • Unclassified names: 900 of the 109,220 taxon names (0.8%) have no classification.
